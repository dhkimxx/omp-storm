# 0.30.0 통합: 감독이 고른 격리 작업만 부모 트리에 씁니다

이 문서는 0.30.0이 준비하는 격리 작업 통합의 동작과 경계를 적는다. 0.29.0은 격리 워커의 결과를 **보관**만 하고
부모 트리에 반영하지 않았다. 0.30.0은 그 보관된 결과 가운데 감독이 **정확한 후보 ID로 고른 것만**, 살아 있는 사용자
요청 아래에서, 한 번에 하나씩 부모 트리에 씁니다. 수용 판정은 그대로 기존 평가기와 리뷰가 합니다. 쓰기 영수증은
수용이 아닙니다.

## 릴리스 상태

**고정 호스트 omp 19.2.1에서는 관리되는 격리 실행(후보 생성)을 켜지 않는다.** 호스트는 `task` 도구에서
`{ requested }`만 받고, 자동 적용·병합은 스폰 훅 전에, 격리 백엔드는 훅 뒤에 읽는다. 그 뒤 읽기에서
`isolation.backend`가 `auto`로 바뀌고 `ovnfs.path`가 해석되면 플러그인이 보지 못하는 사이 ovnfs 체크아웃이
선택될 수 있다. 플러그인은 그 읽기를 관찰하거나 고정할 수 없으므로, 이 호스트에서 "네이티브 경로가 디스패치마다
같다"는 것을 증명할 수 없다. 증명 없는 실행은 켜지 않는다.

따라서 이 호스트의 0.30.0은 다음 상태다.

- 0.29.0의 보존 동작(패치·브랜치·체크아웃, `부모 밖 보존`)이 그대로다. 이 문서의 `storm candidates`/`integrate`는
  후보를 만들지 않으며, 보존된 0.29.0 산출물을 통합 후보로 승격하지 않는다.
- 캡처·델타·기록·후보 조회·쓰기·울타리 코드는 들어가지만, 관리되는 비공개 실행의 문은 닫혀 있다.
- 호스트가 **해석된 workspace factory 또는 백엔드 결정과 불투명 토큰을 스폰 훅 전에 한 번 고정하고, 같은 factory를
  디스패치에 쓰며, 자식 진입에서 그 토큰과 실제 자식 연관을 돌려주는** 경계를 제공한 뒤에만 이 호스트에서 켤 수
  있다. 그 전에는 `scripts/e2e/integration-pin.ts`의 `backend-late-read` 게이트가 `BLOCKED`다.

이 문서의 나머지는 그 경계가 갖춰진 호스트에서의 계약이다. 고정 19.2.1에서 아래 명령을 "지금 되는 기능"으로
읽지 않는다.

## 사용자가 하는 일

1. 격리 구현자를 계획 레인이나 계획 밖 `isolated: true` 항목으로 보낸다. 워커는 자기 체크아웃에서 일하고 끝나면
   Storm이 캡처를 봉인한다.
2. 실행이 살아 있는 동안 감독이 `storm candidates`로 후보를 읽는다. 기본 보기는 진행 중인 이 실행의 후보이고,
   실행이 없으면 가장 최근에 권한이 있었던 기록을 보여 준다.
3. 감독이 정확한 후보 ID를 `storm integrate`에 넣는다. 그 밖의 ID, 중복, 다른 실행의 ID, 형식이 틀린 ID가 하나라도
   있으면 **호출 전체를 쓰기 전에 거절**한다. `all`·범위·접두사·암묵적 선택은 없다.
4. Storm이 후보의 입력 의존을 위상 순서로, 같은 단계 안에서는 배치 순서와 ID로 정렬해 하나씩 쓴다. 쓰기는 기존
   대상 쓰기 잠금과 배타적 통합 홀더 아래에서만 일어난다.
5. 끝나면 각 후보의 쓰기 상태와 쓰지 못한 이유를 돌려준다. 일부만 시작한 경우 나머지는 자동으로 이어 가지 않고,
   새 선택을 요구한다.

`storm candidates`의 기본 보기는 개수·세 가지 예·최대 20개 ID의 한 페이지다. `candidateAfter`는 그 페이지 뒤를
읽는 배타적 커서이고, `candidateId`는 정확한 한 ID의 상세다. `candidateRunId`는 지난 실행의 기록을 읽기 전용으로
보는 것이다. 상세는 출처(실행·디스패치·캐리어·체크아웃 주장), 결과와 중단 원인, 봉인된 번들 종류, Storm 사본과
네이티브 패치·브랜치, 확인된 체크아웃, 변경된 경로 경고, 결과 행 상태를 보여 준다.

## 어떤 캡처가 후보인가

- **성공한 루트 전용 패치.** 호스트가 실제로 낸, 잘린 항목이 없는 정규 파일 텍스트 추가·수정·삭제, 또는 같은
  모드의 전체 인덱스 바이너리 수정만 후보가 된다. 동기 결과, `wait`, 푸시 세 경로 모두 같은 캡처로 이어져야 한다.
- **빈 캡처는 별도 결과다.** 0바이트 루트와 명시적 빈 동반 목록은 "호스트가 루트·중첩 변경을 내지 않았다"는
  뜻이고, 트리가 그대로라는 뜻이 아니다. 중첩 목록이 없는 것은 빈 목록이 아니라 `unknown`이다.
- **보관 전용.** 브랜치, 중첩 저장소, 루트+중첩, 실패·취소된 캡처, 캡처 실패로 남은 작업 공간, 모드만 바뀐 항목,
  순수 이름 변경, 심볼릭 링크·gitlink·특수 모드, 안전하지 않은 경로·별칭은 후보로 보여 주되 **쓰지 않는다**.
  브랜치는 복구 참조이고 설치 형식이 아니다.
- **늦은 캡처.** 기한이 지난 뒤 도착한 결속된 캡처는 복구 관찰일 뿐 새 후보·판정·승격이 아니다. 별도의 모순이
  확인되면 쓰지 않은 준비 상태만 철회한다.

## 쓰기 규칙

- **정확한 만진 전상태.** 후보마다 자기 체크아웃의 기준(HEAD+스테이징+언스테이징+추적하지 않는 WIP)에서 만진
  경로의 바이트·모드·부재를 증명한다. 파동 전체의 기준이나 현재 HEAD를 전상태로 쓰지 않는다.
- **인덱스와 무관한 WIP는 보존.** 설치기는 `--index`·`--3way`·`--reject`·공백 재작성 없이 고정된 델타만 적용하고
  인덱스를 쓰지 않는다. 만지지 않은 스테이징·언스테이징·추적하지 않는 파일은 그대로 둔다.
- **충돌은 만진 경로의 드리프트.** 같은 파일의 겹치지 않는 헝크도, 같은 이름의 추가도 충돌이다. 깨끗한 트리를
  요구하지 않는다. 추적 중인 더러운 파일이나 추적하지 않는 파일의 삭제는 거부한다. 지금 파일이 안전해 보여도
  인덱스·토폴로지가 충돌하면 쓰지 않는다.
- **한 후보의 한 항목이라도 지원하지 않으면 매니페스트 전체를 거부.** 일부만 적용하거나 되돌리지 않는다.
- **쓰기 영수증은 한 번 쓴 것의 유일한 멱등 증거.** 의도·울타리 포인터를 동기화해 남기고, 설치기를 고정해
  디스패치하고, 끝을 증명하고, 정확히 다시 읽은 뒤에만 영수증을 남긴다. 같은 후상태가 이미 있는데 영수증이 없으면
  "있음, 출처 미증명"이지 성공이 아니다. 수동 적용이나 다른 도구가 만든 바이트를 Storm의 쓰기로 인정하지 않는다.
- **울타리.** 디스패치 뒤 끝을 증명하지 못했거나 혼합 상태면 대상 울타리를 유지하고 선택을 멈춘다. 시간 초과,
  재시작, 후보 사라짐으로 울타리를 지우지 않는다. 시작 시 점검은 읽기 전용이다. 사용자가 `/storm` 메뉴에서 직접
  확인한 경우에만, 끝과 전/후 상태가 모두 증명된 정확한 울타리를 풀 수 있다. 풀어도 영수증을 만들거나 바이트를
  복원하지 않는다.

## 판정과 의존

쓰기 영수증은 수용이 아니다. 컨트롤러가 원래 시도와 결과 ID를 기존 평가기·위치·검사·리뷰에 다시 넣고, 원래 범위와
귀속 가능한 변경의 교집합만 격리 `change`의 증인이 된다. 격리 생산자에게 `need: integrated`는 같은 실행의 아직
있고 현재 유효한 영수증과 결과별 위치가 있어야 충족된다. 결과 없는 생산자는 결과 행 대신 발자국 버전을 쓴다.
보존된 `artifact`는 매핑된 간선을 만족할 수 있지만 그 결과 자체가 통합되는 것은 아니다. 경로 없는 `artifact`와
`answer`는 대상 파일을 인증하지 않는다. 지난 실행의 캡처는 볼 수는 있어도 새 실행에서 선택할 수 없다.

## 저장·자원·한계

- 한 실행의 버전 있는 저널/사이드카 하나와 대상 울타리, 소유자 범위의 사본. 소유자 프로필의 통합 저장은 사본과
  저널을 합쳐 2 GiB, 실행별 저널은 64 MiB다. 쓰기 전에 닫는 공간을 예약하고, 넘치면 안전하게 거부한다. 증명된
  기록이나 사본을 조용히 버리지 않는다.
- 캡처는 원본 패치 하나 64 MiB, 매니페스트당 타입 있는 부분 8개, 실행당 소유 패치 256 MiB, 감독당 동시 캡처 복사
  8개까지다. 델타 증명은 펼친 전+후 데이터 64 MiB, 후보당 만진 경로 4,096개에서 시작한다. 이 한도는 작업자 수
  한도가 아니라 입출력·저장 한도다.
- 100개의 작은 후보 선택을 지원한다. 후보마다 전체 워크트리를 훑거나 작업 목록을 반복해 읽거나 인덱스 전체를
  해시하지 않는다. 개요는 개수·예·페이지로 제한하고, 정확한 상세만 더 보여 준다.
- **16개 동시 워커는 주 스레드 구성에서만 주장한다.** `task.workerThreads: 0`이 통제이고, 기본 풀 스레드 구성에서는
  기존 풀 스레드 정지가 그대로 적용된다. 0.30.0은 이 정지를 없애지 않으며 풀 스레드 동등성을 주장하지 않는다.
- **셸은 협조적이다.** 격리는 작업 위치이고 파일시스템 차단벽이 아니다. 워커의 셸이 절대 경로로 부모나 다른 곳을
  쓸 수 있고 Storm은 그것을 보지 못한다. 임의 셸을 파싱해 막지 않는다.
- **네이티브 정리는 Storm의 일이 아니다.** 호스트가 체크아웃을 거둘 수 있고, 브랜치와 패치는 별개 수명이다.
  Storm은 소유한 사본을 자동으로 지우지 않으며, 유일한 보관 사본을 지우지 않는다. 세션 종료가 체크아웃 정리를
  보장하지 않는다.

## 확인 방법

```sh
# 고정 빌드·프로필과 릴리스 게이트 확인 (모델 호출 없음)
E2E_KEEP=1 ./node_modules/.bin/bun scripts/e2e/integration-pin.ts

# 실제 호스트 시나리오 하나씩 (통합 경계가 켜진 빌드에서)
INTEGRATION_MANAGED_LAUNCH=1 E2E_ONLY="carrier: sync root-only" ./node_modules/.bin/bun scripts/e2e/integration.ts
INTEGRATION_MANAGED_LAUNCH=1 INTEGRATION_GROUP=write ./node_modules/.bin/bun scripts/e2e/integration.ts
# 릴리스 게이트를 실제로 실패시키려면 INTEGRATION_REQUIRE_GATES=1을 더한다.

# 격리·쓰기 경계가 있는 비공개 테스트 바이너리에서 실제 동시 실행과 기본 풀 정지 확인
OMP_BIN=/path/to/private/omp E2E_SCALE=1 E2E_SCALE_HOST=1 ./node_modules/.bin/bun scripts/e2e/integration-scale.ts
```

`integration-pin.ts`는 고정 커밋·패키지·락·호스트 19.2.1·OS/Git·프로필을 확인한다. 호스트 소스 검토는
`SOURCE-REVIEWED`로만 인용한다. `backend-late-read`는 `BLOCKED`, 미실행 시나리오는 `NOT-RUN`이다.
실제 캐리어·쓰기·판정은 `integration.ts`에서 시나리오별로 검증한다.

배포본 소스에서는 `task-isolation-payload`와 `apply-before-hook`의 실행 순서를 확인했다. `backend-late-read`는
여전히 **BLOCKED**다. `INTEGRATION_REQUIRE_GATES=1`이면 이 배포본에서 종료 코드 2를 반환한다.

별도로 빌드한 비공개 `omp/19.2.1`에서는 동기·`wait`·푸시와 혼합 배치, 빈 `wait` 중복 방지, 정확한 후보 상세,
사용자의 기존 변경·인덱스를 보존하는 설치, 삭제 거부, 설치 영수증에 따른 수용과 `need: integrated`를 실제 세션에서 확인했다.
`task.workerThreads: 0` 통제에서는 4·8·16개 작업자의 모델 요청과 셸이 각각 실제로 겹쳤다.
각 시나리오에서 작업자 수만큼 물리 체크아웃·봉인·사본이 확인됐고, 선택하지 않은 부모 트리는 그대로였다.
이 검증은 배포본의 호스트 경계를 바꾸지 않으며, 기본 작업자 풀에서의 100개 동시 실행을 증명하지 않는다.
