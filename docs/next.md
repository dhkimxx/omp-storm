## 열린 결정

| 항목 | 왜 열려 있나 | 후보 |
|---|---|---|
| 가드레일 완화 | 지금은 막는 쪽이 기본이다. 외부 리뷰는 감독의 직접 수정 허용, 큰 재읽기 경고, 승인 없는 워커 상한 확대, 모델 능력 레지스트리를 제안했다 | 실제 실행의 막힌 호출과 그 뒤 감독이 한 일을 근거로만 하나씩 완화한다 |
| LICENSE | 저장소에 라이선스 파일과 `package.json`의 `license`가 없다 | 라이선스를 고른다 |
| 리뷰의 폴백이 구현의 주 모델과 같을 수 있다 | 폴백은 다른 Provider의 검증된 경로에서 고르는데, 리뷰와 구현의 계열 분리는 가격 계층보다 뒤에 본다 | 폴백에서도 계열 분리를 앞세우기, 그대로 두기(폴백할 때만 독립 리뷰를 잃는다) |
| 검증된 경로를 앞세우면 폴백 품질이 내려갈 수 있다 | 실제 데이터에서 탐색·단순 작업의 폴백이 주 모델보다 점수가 꽤 낮은 검증된 경로가 됐다 | 품질 차이에 한도 두기, 그대로 두기 |
| 손으로 쓴 예전 팀 설정 가운데 이제 오류가 되는 모양 | 구현 역할이 없거나, Storm 역할이 아닌 키나 에이전트 이름을 쓴 설정이다. Storm이 쓴 적은 없는 모양이다 | 그대로 오류로 두기, 읽을 때 경고로 낮추기 |
| 승인 기록 한도가 브랜치를 가리지 않는다 | 저장소의 모든 worktree와 브랜치가 승인 저장소를 함께 쓴다. 다른 브랜치의 지금 승인이 한도 밖으로 밀리면 다시 승인해야 한다 | 브랜치별로 지금 승인을 지키기, 그대로 두기 |
| 스파이크 하네스(B0, M0)의 프로필 위치 | omp 동작 확인용으로 남겼고 타입 검사만 한다. 돌리면 실제 홈의 `~/.omp/profiles/storm-b0`, `storm-m0`에 프로필을 만든다 | E2E처럼 홈을 작업 폴더로 돌리기, 그대로 두기 |

## 확인하지 못한 것

| 항목 | 이유 | 방법 |
|---|---|---|
| 0.10의 효과: 감독 비용 비중, 감독 읽기 가운데 서브에이전트와 겹치는 비율 | 0.10은 실제 실행으로 재지 않았다. 기준은 0.8 실행이다 | 실제 실행의 요약 색인으로 비교 |
| 자동 위임의 실모델 고정비 | 격리 회귀는 실행 경로만 확인하고 모델의 판단·Provider 지연·실비를 재지 않는다 | 갤럭시북에서 동일 조회·한 줄 수정·복합 작업을 직접 OMP / 수동 Storm / 자동 위임으로 비교: 첫 워커까지 시간, 메인 요청 수, 결과 크기, 압축 횟수, 실제 변경·검증과 비용 |
| 실제 모델이 근거 위치를 붙이는지, 막힌 읽기와 후속 지시에 어떻게 대응하는지 | 가짜 LLM으로만 확인했다 | 실제 실행의 기록에서 확인 |
| 요청 분류의 정확도와 비용, 실제 모델이 JSON 하나로만 답하는지 | 사이드 턴을 실제 모델로 돌려 재지 않았다. 답을 못 읽으면 사용자에게 묻는 쪽으로 넘어간다 | 실제 세션에서 요청 종류별로 확인 |
| 실제 모델이 라운드 메시지에 어떻게 반응하는지 | 가짜 LLM으로만 확인했다. 실제 모델이 라운드를 받고 팀을 다시 쓰는지 보지 못했다 | 실제 실행의 기록에서 확인 |
| 리뷰 판정이 얼마나 엄격한지 | 검증은 판정의 엄격함만큼만 엄격하다. 리뷰어가 관대하면 `correct`가 검증을 뜻하지 않는다 | 실제 실행의 지적과 판정을 본다 |
| 읽기만 하는 실행이 커버리지·로그 같은 파일을 만들거나 추적되는 파일을 다시 써서 리뷰 라운드가 한 번 붙는 일이 실제 저장소에서 잦은지 | 리뷰가 필요한 팀에서는 0.12가 그렇게 동작하지만 빈도를 재지 않았다 | 실제 실행의 라운드 기록을 본다 |
| git 저장소가 아니거나 커밋이 없는 폴더의 셸 변경 | 시작 커밋이 없어 보지 못한다 | git 저장소에서 쓴다 |
| 하위 모듈 안의 내용 | 비교하지 않는다 | 필요하면 비교를 추가한다 |
| 실행이 죽었는지 판단 | 프로세스 id만 보므로 id가 재사용되면 죽은 실행이 정리되지 않고, 같은 저장소를 쓰는 다른 pid namespace의 실행은 다음 쓰기 전까지 중단으로 표시될 수 있다 | 프로세스 시작 시각까지 비교하기, 그대로 두기 |
| 실제 모델이 이어 가기 인계문을 어떻게 쓰는지 | 가짜 LLM으로만 확인했다. 이전 계획과 작업 트리를 읽고 남은 일을 찾는지 보지 못했다 | 중단된 실행을 실제 모델로 이어 가 본다 |
| 실제 모델이 레인을 올바르게 연결하고 남은 레인을 처리하는지 | 자동 위임은 스폰과 레인 상태를 연결하지만 실제 모델의 과도한 재계획·누락은 별도 문제다 | 실모델 기록에서 레인 상태, 스폰, 재계획 이유를 비교한다 |
| 실제 TUI에서 `agent_end` 처리기 안에서 보낸 실행 계약·라운드 메시지의 순서 | 소스로만 봤다 | TUI E2E에 시나리오 추가 |
| 메시지가 밀려 있는 동안의 기다림 | omp가 밀린 메시지를 계속 보고하면 그만큼 기다린다. 실제 세션에서 확인하지 않았다 | 실제 실행에서 밀린 메시지가 있는 세션으로 확인 |
| 승인 창의 "전체 내용 보기"를 끝까지 읽었는지 | 열었는지만 본다. 끝까지 스크롤했는지는 보지 않는다 | 필요하면 스크롤 끝을 조건으로 삼는다 |
| 범위 없는 읽기의 쪽 크기 | 기본값으로 센다. 사용자가 omp의 `read.defaultLimit`을 올렸으면 실제보다 적게 센다 | 설정을 읽을지 정한다 |
| ACP 클라이언트에서의 표시 | TUI가 아닌 곳에서는 알림과 현황을 대화 기록 메시지로 보낸다. 클라이언트가 그것을 보여 주는지 확인하지 못했다 | ACP 클라이언트에서 확인 |
| 폼을 지원하지 않는 ACP 클라이언트의 판별 | 그런 클라이언트에서도 폼 기능이 있는 것으로 보인다. 지금은 선택 창이 답 없이 끝나 아무것도 바뀌지 않는다 | 폼 미지원 클라이언트에서 확인 |
| 격리 팀의 읽기 기록 | 서브에이전트가 다른 작업 트리의 경로를 읽어 감독의 경로와 맞지 않을 것으로 본다 [추정] | 격리 팀의 실제 실행 |
| 폼을 그리는 ACP 클라이언트에서의 "역할별로 고르기" | TUI와 폼 파서로만 확인했다 | 폼 지원 클라이언트에서 확인 |
| Orca 채팅의 `elicitation.form` 지원 | 미지원이면 Orca 채팅에서는 승인할 수 없다 | Orca에서 omp 채팅을 열고 승인 창을 띄운다 |
| 숫자 칸의 커서 위치 | omp 폼의 숫자 칸은 커서가 값 앞에서 시작한다. 그대로 치면 값 앞에 붙는다(4에 3을 치면 34). 범위를 넘으면 omp가 제출을 막고, 범위 안이면 승인 창의 변경 내용에 보인다 | 워커 수와 병렬도처럼 범위가 작은 값은 선택 칸으로 바꿀지 정한다 |
| 실제 비동기 서브에이전트가 있는 TUI에서의 실행 중 압축 | UI 없이 도는 경로만 확인했다 | 실제 실행 |
| 기본 보관 시간에서의 정리, TUI에서의 B0 결과 | B0는 짧은 보관 시간과 RPC만 돌렸다. E2E는 같은 모양의 파일을 심어 확인했다 | 정리를 켠 팀의 실제 실행 |
| 부속 파일, 종료 표시, 중첩 폴더가 실제로 있을 때의 삭제 | B0의 서브에이전트는 이것들을 만들지 않았다 | 구조화 출력·중첩 스폰 시나리오를 spikes/b0에 추가 |
| eval 자식의 진행 중 비용 이벤트, `ctx.abort()`가 자식을 어디까지 멈추는지 | 예산 누계와 실행 중단의 정확도 | 하네스에 시나리오 추가 |
| `omp stats --summary` 증분 갱신 시간 | 사용 기록 갱신의 비용 | 실제 DB 사본을 둔 프로필에서 측정 |
| `ctx.modelRegistry`의 실제 지능 점수 커버리지 | 시뮬레이션값만 있다 | 실제 프로필의 탐지 결과에서 측정 |
| 카탈로그 모델로 처음 라우팅할 때의 기능 확인 프로브 | 시험 사용 비용에 들어간다 | 실제 모델 경로에서 확인 |
| 쿼터 한도의 등급 이름이 모델 id의 낱말과 겹칠 때 | 요금제 이름이 모델 이름과 같으면 엉뚱한 모델이 소진으로 잡힐 수 있다. 실제 `omp usage` 출력으로 보지 않았다 | 실제 쿼터 보고로 확인 |
| `/agents` 허브의 플러그인 역할 에이전트 표시 | P0 Q3의 일부 | TUI에서 확인 |
| 재시작 뒤 omp vibe 워커 복원 | M0에서 관찰하지 못했다. Storm이 omp vibe에 들어가지 않는 동안은 영향이 없다 | omp vibe를 쓰게 되면 확인 |

- **새 파일 비교의 한도:** 2MB가 넘는 새 파일은 크기와 수정 시각으로, 새 파일이 2,000개를 넘으면 이름만 비교한다. 전체 diff는 메모리에 읽는다.
